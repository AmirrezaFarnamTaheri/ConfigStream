In both ecosystems you’re really just “tag-wiring” one outbound to use another outbound as its upstream dialer. The names differ:

* V2Ray/Xray (what v2rayN drives): `proxySettings.tag`
* sing-box: `detour`

### v2rayN (V2Ray/Xray JSON): `proxySettings.tag`

v2rayN is a GUI wrapper around a V2Ray/Xray-core style config with `outbounds` that each have a `tag`. Chaining is done by putting a `proxySettings` object on an outbound and pointing it at the *tag* of the upstream outbound. The official V2Ray config calls this `ProxySettingsObject`, and it’s exactly for delegating an outbound’s traffic to another outbound. ([V2Ray][1])

Minimal pattern:

```json
{
  "outbounds": [
    {
      "tag": "proxy-main",
      "protocol": "vless",
      "settings": { /* your VLESS/VMess/Trojan settings */ },

      "streamSettings": { /* ws/grpc/tls/reality/etc */ },

      "proxySettings": {
        "tag": "upstream"
      }
    },

    {
      "tag": "upstream",
      "protocol": "socks",
      "settings": {
        "servers": [
          { "address": "127.0.0.1", "port": 1080, "users": [] }
        ]
      }
    }
  ]
}
```

What that means in plain language:

Traffic that *would* go out via `proxy-main` is instead “dialed” through the outbound tagged `upstream` first (e.g., a local SOCKS/HTTP proxy, a VPN app exposing a local port, etc.). The key is that `proxySettings.tag` must match an existing outbound `tag`. ([V2Ray][1])

Multi-hop chaining in V2Ray/Xray is just repeated delegation:

```json
{
  "outbounds": [
    { "tag": "hop3", "protocol": "vless", "settings": {}, "proxySettings": { "tag": "hop2" } },
    { "tag": "hop2", "protocol": "socks", "settings": {}, "proxySettings": { "tag": "hop1" } },
    { "tag": "hop1", "protocol": "http",  "settings": {} }
  ]
}
```

Notes that bite people:

1. This is *client-side* chaining (your local core reaches the final outbound via an upstream proxy). It is not automatically “server A forwards to server B” unless you also configure forwarding/relay behavior on the servers.

2. Different transports over an HTTP CONNECT upstream can be fragile in some implementations (WebSocket-over-CONNECT issues come up fairly often). If something fails only when chained, test with plain TCP first to isolate the failure mode. ([GitHub][2])

### sing-box JSON: `detour` (tag of upstream outbound)

sing-box has a shared “Dial Fields” concept. The relevant field is `detour`, defined as “the tag of the upstream outbound”; when set, it forwards dialing to that outbound. ([Sing Box][3])

The exact placement is “as a dial field” in an outbound. In most configs you’ll see it directly inside the outbound object (because those dial fields are “shared” across outbound types):

```json
{
  "outbounds": [
    {
      "type": "vless",
      "tag": "proxy-main",
      "server": "example.com",
      "server_port": 443,
      "uuid": "…",
      "tls": { "enabled": true },

      "detour": "upstream"
    },
    {
      "type": "socks",
      "tag": "upstream",
      "server": "127.0.0.1",
      "server_port": 1080
    }
  ]
}
```

Multi-hop in sing-box is the same conceptually:

```json
{
  "outbounds": [
    { "type": "vless", "tag": "hop3", "server": "c.example", "server_port": 443, "uuid": "…", "detour": "hop2" },
    { "type": "http",  "tag": "hop2", "server": "127.0.0.1", "server_port": 8080, "detour": "hop1" },
    { "type": "socks", "tag": "hop1", "server": "127.0.0.1", "server_port": 1080 }
  ]
}
```

Important sing-box caveat: not every outbound type can be meaningfully detoured through every other outbound type. There are open issues/limitations around detouring certain proxy protocols through other proxy protocols (especially when TLS/handshake expectations differ). In practice, detouring via SOCKS/HTTP is the most common “works everywhere” approach. ([GitHub][4])

Extra related “detour” knobs you may run into:

* Some components (like remote rule-set downloads) can also specify which outbound tag to use for fetching (e.g., `download_detour`). ([Sing Box][5])

### Quick mental model

* v2rayN/V2Ray/Xray: **Outbound A** has `proxySettings.tag = "B"` ⇒ A delegates to outbound **B**. ([V2Ray][1])
* sing-box: **Outbound A** has `detour = "B"` ⇒ A dials through outbound **B**. ([Sing Box][3])

So if you’re translating configs between the two, “`proxySettings.tag` ≈ `detour`”, and “outbound `tag`” is the shared glue concept.

If you keep the chain to SOCKS/HTTP as the intermediate hops, you’ll avoid a lot of weird edge cases and protocol-mismatch pain.

With “nekoray-core” (people also mean **NekoRay / NekoBox for PC’s core backend**), there isn’t a brand-new third JSON dialect. It’s a GUI that spits out (or embeds) the config format of whatever core you’re running underneath.

Two practical consequences:

1. Modern NekoRay/NekoBox-for-PC is primarily **sing-box backend**, and the project repo notes it’s “backend: sing-box” (and the repo is archived/read-only as of Mar 17, 2025). ([GitHub][1])
2. Older NekoRay versions (and “custom core” setups) have used **v2ray-core / xray-core** in certain version ranges; the README credits v2ray-core and Xray-core for older versions, then sing-box. ([GitHub][1])

So chaining is:

* sing-box mode → `detour`
* v2ray/xray mode (if you’re using that core externally / older builds) → `proxySettings.tag`

### If your NekoRay is using sing-box core (most common today)

Chaining is the sing-box way: you set an outbound’s **`detour`** to the tag of another outbound that acts as the upstream hop. That “detour” field is documented as a shared dial setting in sing-box, and is used in multiple parts of sing-box config to say “connect via outbound X.” ([sing-box.sagernet.org][2])

Minimal example (VLESS through a local SOCKS upstream):

```json
{
  "outbounds": [
    {
      "type": "vless",
      "tag": "proxy-main",
      "server": "example.com",
      "server_port": 443,
      "uuid": "…",
      "tls": { "enabled": true },

      "detour": "upstream"
    },
    {
      "type": "socks",
      "tag": "upstream",
      "server": "127.0.0.1",
      "server_port": 1080
    }
  ]
}
```

Multi-hop is just chaining detours:

```json
{
  "outbounds": [
    { "type": "vless", "tag": "hop3", "server": "c.example", "server_port": 443, "uuid": "…", "detour": "hop2" },
    { "type": "http",  "tag": "hop2", "server": "127.0.0.1", "server_port": 8080, "detour": "hop1" },
    { "type": "socks", "tag": "hop1", "server": "127.0.0.1", "server_port": 1080 }
  ]
}
```

How this maps to the NekoRay GUI: create one profile/connection that represents the upstream proxy (HTTP or SOCKS), then create your “real” proxy profile (VLESS/VMess/Trojan/etc), and set the real one to go through the upstream hop. A Russian-language sing-box/Nekobox write-up describes exactly this workflow and explicitly mentions sing-box “detour” chaining via an HTTP/SOCKS corporate proxy. ([Habr][3])

### If your setup is actually using Xray/V2Ray core (older NekoRay builds or external “core”)

Then you’re back in V2Ray/Xray JSON land. Chaining is done via:

```json
"proxySettings": { "tag": "upstreamOutboundTag" }
```

So the equivalent concept is: outbound A delegates dialing to outbound B by tag.

Example:

```json
{
  "outbounds": [
    {
      "tag": "proxy-main",
      "protocol": "vless",
      "settings": { /* … */ },
      "streamSettings": { /* … */ },
      "proxySettings": { "tag": "upstream" }
    },
    {
      "tag": "upstream",
      "protocol": "socks",
      "settings": { "servers": [{ "address": "127.0.0.1", "port": 1080 }] }
    }
  ]
}
```

### What about “custom core” inside NekoRay?

NekoRay/NekoBox for PC supports “Custom Config” and “Custom Core” entries (NaïveProxy, Hysteria2, etc.) according to its README. ([GitHub][1])
Those don’t magically introduce a new chaining schema either; you chain using whatever that custom core’s native config supports. If you’re still using sing-box for those outbounds, it’s still `detour`. If you truly run a different binary/core, you follow that binary’s config model.

### Quick sanity checklist (because chaining fails in boring ways)

* Every hop needs a unique `tag`, and `detour` / `proxySettings.tag` must reference an existing tag.
* Keep intermediate hops simple first (SOCKS/HTTP upstream) before attempting “proxy protocol over proxy protocol” complexity; it isolates whether the problem is routing vs. transport/handshake.
* In sing-box, “detour” can appear in more than just outbounds (example: DNS servers can specify a detour outbound used to reach the resolver). ([sing-box.sagernet.org][2])

Bottom line: for “nekoray-core,” the chaining JSON format is whichever backend you’re using—today that usually means sing-box and `detour`. ([GitHub][1])
